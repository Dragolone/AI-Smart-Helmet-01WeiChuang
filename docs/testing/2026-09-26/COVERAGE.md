## 3. 本轮新增：启动对账「不该补建」守卫（`backend/test/audit-sos-reconcile.e2e-spec.ts`）

`sos-scheduler` 分支覆盖 55%，未覆盖的除日志三元外，恰是两条防重复建单的守卫。写错的后果是**服务重启时给紧急联系人重复发短信**、或给设备前主人建单。既有 ①b 只测了「该补建的补建了」。

| 用例 | 断言 |
|---|---|
| ① 事件发生时设备从未绑定 | 不建单 |
| ② 事件发生在前主人解绑之后 | 不给前主人补建 |
| ③ 事件发生时已有进行中的单、**重启时那一单已结束** | 不为旧事件新建一单、不发短信 |
| ④ 对照：上一单结束之后才发生的事件 | 照常补建（守卫不能过宽） |

**变异验证**：删合并守卫 → ③ 红；删解绑时间条件 → ② 红；原代码 4/4 绿。

**过程记录（为什么要做变异验证）**：第一版测试用「当前时间 − 1 s」做事件时间，整个套件 1 s 内跑完，事件时间早于绑定/建单时间——① ② ③ 全部因为「事件发生时根本没绑」而通过，测的不是目标条件；两个变异都存活才暴露出来。改为以数据库真实时间戳为锚（`unboundAt / createdAt / finalizedAt + 20 ms`）；③ 另补上守卫真正要防的一步——重启前那一单已结束（否则 `createOrMerge` 自己的合并会兜住，守卫是否存在都测不出来）。
