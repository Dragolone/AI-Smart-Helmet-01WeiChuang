# 新成员从零上手指南

> 写给第一次做 App 开发的你。目标不是让你背下所有细节，而是**理解这个项目在做什么、为什么这么做、你从哪里下手**。
> 你有 Claude Code——它是你的结对导师。本文告诉你"问什么、按什么顺序"，具体操作让 Claude 带你。

---

## 一、这个项目在做什么（5 分钟版本）

我们在给一款**智能滑雪头盔**做配套软件。头盔硬件和 AI 识别算法由其他团队做，**我们只做软件**：手机 App + 云端后端 + 管理后台。

**产品要解决的问题**（老板定的三条必保）：

1. **摔倒救援**：滑雪的人摔了，头盔检测到，App 上 60 秒倒计时——没人取消就自动短信/推送通知紧急联系人，附上事故位置
2. **后方预警**：有人从后面快速接近时，头盔当场响（硬件做的），手机同步收到记录（我们做的）
3. **队友对讲**：头盔当蓝牙耳机，通过 App 和网络跟队友实时通话（像开黑语音）

**一句话记住我们的边界**：硬件采集 → 算法判断 → **软件只接收结果、完成业务流程**（保存、展示、通知、记录）。我们永远不做"判断这个人摔没摔"这种事——那是算法团队的活，我们只处理"算法说他摔了"之后的一切。

## 二、系统全貌（数据怎么流动）

```text
头盔（内置 4G 卡 + GPS + 蓝牙）
  │
  │ ① 头盔自己通过 4G 上报：位置、电量、摔倒、危险事件
  ▼
云端后端（我们写的，NestJS）
  │ 收到 → 校验 → 存数据库（PostgreSQL）→ 该通知就通知
  ▼
手机 App（我们写的，React Native，安卓 + 苹果双端）
  │ ② 从后端拉数据/收实时推送：地图看位置、SOS 倒计时、事件历史
  │ ③ 对讲：头盔≈蓝牙耳机 ←蓝牙→ 手机 App ←4G→ RTC 语音云服务 ←→ 队友
  ▼
管理后台（我们写的，网页）：运营人员看用户/设备/事故记录
```

三个关键理解：

- **头盔和手机是两条独立通道**。头盔用自己的 4G 卡上报数据（人摔了手机可能飞了，头盔必须自己能求救）；手机只在对讲和近场功能时跟头盔打交道
- **真头盔还没造出来**。我们用一个"Mock 设备模拟器"（一段程序）假扮头盔发数据，后端完全分不出真假——所以硬件没就绪完全不挡我们开发
- **没信号怎么办**：头盔本地攒着数据，恢复信号自动补传，一条不丢（协议里设计好了）

## 三、你需要知道的几个词

| 词 | 意思 |
|----|------|
| Monorepo | 一个 Git 仓库装下全部子项目（app / backend / admin / mock-device） |
| Contract | 「接口契约」文档：约定谁给谁传什么字段、什么格式。**先改文档再写代码**是本项目铁律 |
| MQTT | 物联网设备和云端之间的消息协议（头盔↔云端用它） |
| Mock | "假的但行为一致的替身"：Mock 设备假扮头盔，Mock Provider 假扮短信/推送服务 |
| RTC | 实时音视频云服务（对讲功能租用它传声音，王者荣耀语音同款技术） |
| Prisma / Migration | 数据库工具：表结构改动都通过可审查的"迁移文件"进行，禁止手改数据库 |
| Expo / Development Build | React Native 的开发工具链：一套 TypeScript 代码同时出安卓和苹果两个 App |
| PR / Review | 代码不直接进主干：开分支 → 提交 → 对方看过（Review）→ 合并。两人项目也严格执行 |

## 四、上手路线（按顺序做，预计 1–2 天）

### 第 1 步：装环境 + 跑起来（半天到一天）

照 `plan/weekly-plan.md` 的「新成员第一天上手」一节做。**推荐直接用里面的 Claude 启动指令**——粘贴给你的 Claude，它会带你把 Docker、后端、双端模拟器 App 全部跑起来，每步告诉你应该看到什么。

完成标志：两个手机模拟器上都能打开 App 看到欢迎页，浏览器访问 localhost:3000 能看到 Hello World。**卡住超过 20 分钟就发群里，不要自己闷头熬。**

### 第 2 步：读文档建立理解（半天，重要程度排序）

不用背，读懂"为什么"即可。推荐每读一份就让 Claude 陪读——比如问它：

> 请给我讲解 docs/EVENTS.md：每种事件是干什么的？为什么坐标必须写明坐标系？为什么服务端要按 eventId 去重？

阅读顺序：

1. **CLAUDE.md**（根目录）——项目宪法：范围、规矩、技术栈、12 周计划。你的 Claude 每次都会自动读它
2. **plan/weekly-plan.md** ——每周谁做什么、为了什么
3. **docs/DECISIONS.md** ——所有已拍板的技术决策和理由（为什么不用微服务、为什么头盔直连 4G……有疑问先来这里找答案）
4. **docs/EVENTS.md** 和 **docs/API.md** ——两份 Contract：头盔传什么、App 和后端怎么通信
5. **docs/DEVICE_PROTOCOL.md** ——头盔怎么连云端（MQTT 细节，扫一遍留印象即可）

### 第 3 步：干第一件正事——事后 Review 两份 Contract

EVENTS.md 和 API.md 是负责人先合并的，按规矩欠一次你的 Review。让 Claude 陪你逐节过一遍，凡是看不懂或觉得不合理的地方，直接在群里提问或在 GitHub 上开 Issue。**看不懂的地方大胆问——文档写得让新人看不懂，是文档的问题，不是你的问题。**

### 第 4 步：认领你的角色，进入 Week 2

和负责人对一下你是 Developer A（App 侧）还是 Developer B（后端侧）——分工表在 weekly-plan.md。认领后把你角色下 Week 2 的任务读一遍，让 Claude 给你讲每项任务的背景，然后开工。

## 五、和 Claude 协作的规矩（重要）

1. **Claude 写的代码，你必须逐行看懂、自己测过，才能提 PR**——出了问题责任在人不在 AI，Review 你代码的同事也按"人写的"标准看
2. **让 Claude 先讲方案再动手**：养成习惯说"先告诉我你的思路和要改哪些文件，我确认后再写"
3. **Claude 受项目规矩约束**：它不会（也不该）擅自改 Contract、引入新框架、跳过测试。如果它要这么做，停下来问负责人
4. **多让它解释**："为什么这么写""这段代码在整个流程里处于哪一环"——你是来成长的，不是来当复读机的

## 六、日常开发节奏

- 每天和负责人 10 分钟同步：昨天做了什么、今天做什么、卡在哪
- 写代码：拉最新 main → 开 `feat/xxx` 分支 → 小步提交 → 提 PR → 对方 Review → Squash 合并
- 改公共文件（docs/ 下的 Contract、packages/shared、数据库 schema）**必须先沟通再动手**
- 每周五对照 weekly-plan.md 的验收标准自查

有任何问题：先问你的 Claude → 再查 DECISIONS.md → 还不清楚就群里问。欢迎上车 🎿
